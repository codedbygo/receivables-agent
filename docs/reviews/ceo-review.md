## Review sections

### 1. Architecture

- The layer table in the brief is sound. One risk: the "Tools" layer is the only door for the agent, but the API also mutates state (approve, reject, simulate reply, admin). Both must call the same service functions, or the guardrails and timeline writes diverge. Finding A1: one service layer under both API and tools; guardrails and timeline writes live in services, never in handlers.
- Six containers on a slow machine: api, mcp and worker can be one Python image with three commands. Finding A2 (eng review): one backend image, three entrypoints.

### 2. Error and rescue map

| Method / codepath | Failure | Named error | Rescued? | Rescue action | User sees |
| --- | --- | --- | --- | --- | --- |
| gateway.complete | OpenRouter 429/5xx | LLM_UPSTREAM | Y | backoff, 3 tries | run step marked failed, customer skipped, admin shows error |
| gateway.complete | timeout | LLM_TIMEOUT | Y | same | same |
| gateway.complete | budget spent | BUDGET_EXHAUSTED | Y | no call made | admin banner, GuardrailEvent |
| gateway.complete (replay) | fixture missing | REPLAY_MISS | N (fails loudly by design) | none | error names the key; CI fails |
| draft.assemble | placeholder missing | PLACEHOLDER_MISSING | Y | draft discarded | GuardrailEvent, timeline |
| guardrails.verify | mismatch | AMOUNT_MISMATCH, TOTAL_MISMATCH, INVOICE_NOT_FOUND, INVOICE_WRONG_CUSTOMER, CUSTOMER_MISMATCH, DATE_INVALID, DATE_MISMATCH, TONE_UNSAFE | Y | draft rejected | reason on draft and timeline |
| send worker | SMTP down | SMTP_UNAVAILABLE | Y | retry, then failed | status failed, timeline |
| send (any path) | not approved / kill switch | NOT_APPROVED, SENDING_DISABLED | Y | refuse | error, GuardrailEvent |
| webhook | bad signature / stale | SIGNATURE_INVALID, REPLAY_WINDOW | Y | 401 | nothing stored |
| webhook | duplicate event | (idempotent no-op) | Y | return 200 | nothing changes |
| classify | label outside the seven | CLASS_INVALID | Y | escalate | escalation |
| classify | low confidence | (not an error) | Y | escalate | escalation |
| orchestrator | fifth tool call | STOPPED_LIMIT | Y | stop | outcome badge |

No catch-all handlers: each boundary maps named errors to an HTTP status or tool error envelope; anything unnamed is a 500 with a request id and is logged, never swallowed.

### 3. Security

- Prompt injection through reply text is the top threat (STRIDE: tampering, elevation). Mitigated by read-only tools during classification, delimited data, code-parsed amounts, and the fact that no reply can trigger a send. Threat model (Phase 4) must include it.
- Admin actions (reset, clock) are destructive in a shared demo: admin-only, logged. Carried to auth.
- High severity findings: 0 open (each named threat has a story).

### 4. Data flow and interaction edge cases

- Double-click Approve: idempotent status transition; second call returns the current state (US-00-011 idempotent send covers the send; the approve endpoint must be idempotent too). Finding D1.
- Stale queue: a draft approved in one tab while edited in another. Finding D2: optimistic version column on messages; the second write gets 409 `STALE_DRAFT`.
- Clock advanced while a run is in progress: the run reads the clock once at start. Finding D3.
- Empty states: every panel has one (AC-US-00-003-4, AC-US-00-004-1).

### 5. Code quality

No code yet. Rule to carry: one money formatter per runtime, one clock module, one gateway, one service layer. DRY on these four is what keeps the numbers right.

### 6. Tests

```
  unit (pytest)        priority, tone, parser, guardrails, allocation, promise rules
  service (pytest+pg)  every state change writes timeline; send idempotency; kill switch on all paths
  tool (MCP client)    one test per tool, both transports (spike proved the harness)
  eval (replay)        40 replies, >=10 scenarios, red-team set
  e2e (API, replay)    the ABC story, asserting each beat
  ui (Playwright)      one smoke of the story path; accessibility scan
```
Gap: none in plan; the risk is the e2e test drifting from fixtures (0E).

### 7. Performance

Fifteen customers, four calls each at most, is 60 calls per run: about 1 to 2 minutes live and seconds in replay. Not a concern. The dashboard aggregates run over 300 invoices; plain SQL is enough.

### 8. Observability

Required: run id on every log line of an agent run; an admin view of runs, costs and guardrail failures (US-01-006). Heavy dashboards are skipped at hackathon depth.

### 9. Deployment and rollout

- Finding R1: pre-build and pre-pull images before demo day; the slow network makes a cold `docker compose up --build` a real demo risk. Runbook item.
- Finding R2: the demo runs in replay by default; live is shown once as a toggle. Runbook item.
- Rollback: previous image tag plus `make reset-demo` (brief).

### 10. Long-term trajectory

Reversibility 4/5: the channel interface, gateway and service layer are the seams a real product needs. Debt items: simulated inbound replies, seeded ledger instead of an accounting sync.

### 11. Design and UX

- The approval queue is the product's hero screen, not the dashboard: it is where trust is earned (E1).
- Hierarchy on the customer page: outstanding and next action first, timeline second, everything else below.
- Avoid chat UI patterns entirely; the brief asks for an operations console.
