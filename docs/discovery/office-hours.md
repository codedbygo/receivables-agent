## Problem statement

Indian B2B sellers (distributors, manufacturers, wholesalers) carry large receivables and chase them by hand: an accountant exports ageing from Tally or a spreadsheet, phones or WhatsApps customers, writes promises on paper, and matches bank credits to invoices later. Follow-ups slip, broken promises go unnoticed, and disputes surface weeks late. The product is "an AI employee that manages unpaid invoices", but one whose every number comes from the ledger and whose every message a human approves.

## Who pays, and why now

- **Buyer:** owner or finance head of an SME or mid-market B2B business (roughly ₹10 cr to ₹500 cr revenue) with 50 to 500 active credit customers and one to three people on collections.
- **Why now:**
  - Since FY 2023-24, Income Tax section 43B(h) disallows a buyer's deduction for dues to MSME suppliers unpaid past the MSMED Act limit (45 days with an agreement). Sellers now have a statutory lever and a reason to follow up on time. (Assumption to confirm with a domain expert before any claim in the demo.)
  - LLMs are now cheap enough (Haiku tier) to draft and classify every reply for a few paise per customer.
  - Indian B2B communication is email plus WhatsApp; both can be driven by software.
- **Status quo:** Tally ageing report, Excel, phone, WhatsApp, a notebook of promises. Tools like generic dunning add-ons send fixed templates and do not read replies.

## What the demo must prove (in order of judge weight)

1. **Numbers cannot be hallucinated.** A draft with a wrong amount or a fake invoice is rejected by code, live, with a visible GuardrailEvent. This is the single strongest trust signal; show a red-team rejection on stage.
2. **A human stays in control.** Approve, edit (re-verified), reject; the kill switch stops every send path.
3. **The loop closes.** Reply becomes a promise, the demo clock advances, a bank credit arrives, the promise is fulfilled and outstanding drops from ₹7,50,000 to ₹4,50,000, all on one timeline.
4. **It is measured.** An evaluation page with accuracy numbers computed from runs, not typed in.
5. **It is explainable.** Priority reasons and the agent trajectory are visible for every customer.

## What makes this cool

The agent is deliberately small. Priority, tone selection, reconciliation and money checks are deterministic code; the model only writes prose around placeholders and classifies replies. The "AI employee" is trustworthy because most of it is not AI.

## Approaches considered

### Approach A: Python monolith with server-rendered UI
- Summary: FastAPI serves both API and Jinja/HTMX pages; tool registry in-process; MCP stdio wrapper over the same registry; APScheduler in-process.
- Effort: M. Risk: Low.
- Pros: one language, one container for app code, fastest to a working vertical slice.
- Cons: weaker "fintech console" polish; the brief asks for a separate web container.

### Approach B: FastAPI API + Next.js console + MCP server + worker (the brief's topology)
- Summary: Postgres, MailHog, `api` (FastAPI), `mcp` (same Python package, streamable HTTP and stdio), `worker` (jobs), `web` (Next.js). Shared tool registry as in premise 3.
- Effort: L. Risk: Med (two stacks, more compose wiring).
- Pros: matches the brief and the judging checklist; strongest UI; clean layer separation for the HLD.
- Cons: two toolchains, two test suites, more time on plumbing.

### Approach C: Claude Code as the agent runtime (lateral)
- Summary: skip the orchestrator; the demo drives Claude Code against the MCP server, with a thin UI for approvals only.
- Effort: S to M. Risk: High for judging.
- Rejected: the brief requires a bounded, logged loop with a 4-call limit and a trajectory viewer; that needs our own orchestrator. Keep the Claude Code registration as a bonus demo beat.

## Recommended approach

**B, built as a vertical slice first.** Order inside P0: schema, seed, priority, gateway in replay, tool registry, bounded agent, drafting with placeholders, guardrails, approval, MailHog send, reply classification, promise, timeline. Then the dashboard. Only then P1. The final stack choice is made at the Phase 3 decision checkpoint; this is the working recommendation.
